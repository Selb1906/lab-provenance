## 5줄 요약

1. **일지의 수치는 저장소의 결과 파일과 전부 일치한다**(실험 13 복원율·오탐 5/152·ORB threshold 46, 실험 14 상위 1·5 적중, 실험 15 회복률·모서리 오차 중앙값, 실험 18 0/20·0/60·13~15/20·89/90, 실험 19·20·21·22·24·25 전부). 결론의 방향도 코드로 뒷받침된다. 수치를 고칠 곳은 없고, **해석과 표본 크기의 서술**을 고칠 곳이 있다.
2. **실험 18의 '0/80'은 그림별 key의 효과가 아니라 정합(registration) 단계의 효과이고, 그 보호는 1% 통계 검정이다.** `align.register`(tools/align.py:70~93)는 짝 4개만 있으면 어떤 아핀이든 돌려주므로 무관한 그림 20장 전부가 '정합 성공'으로 z까지 갔고(summary의 z 20개 모두 None 아님), 엉뚱한 변환으로 뒤섞인 패턴의 z는 N(0,1)이라 0/80은 기대값 0.8건과 다르지 않다(95% 상한 4.5%). 같은 key였던 실험 10(20/20)은 파이프라인 없이 전체 이미지 z를 잰 것이어서 직접 비교가 아니다. 그림별 key만의 효과(평균화 위조에 각 key_i의 전체 이미지 z)는 재지 않았고, 실험 10 데이터로 외삽하면 9개 key의 평균 패턴은 각 key_i와의 상관이 약 1/3로 줄어 전체 이미지 z ≈ 1.4~1.7, 즉 20장 중 약 20~27%가 2.326을 넘을 수 있다[계산 — 3절].
3. **통계: 음원·영상 실험은 합성 10개, 문서 34편이라 10/10의 95% 신뢰구간 하한은 69%, 34/34는 90%다.** 음원 '다른 음원끼리 BER 최소 0.419(45쌍)'와 영상 '다른 영상 매칭 0(90쌍)'은 오탐률 근거로는 각각 상한 7.9%·4.0%일 뿐이다. 실험 22의 포함도 threshold 0.352는 170개 음성에서 정한 표본 내 값이고, 포함도 추정기(tools/dfp.py:49~58, dfp.js:21~28)에는 표본 수 하한이 없어 짧은 질의(수십 단어)에서는 1%를 보증할 수 없다. 11-14 16:45의 'threshold 2는 원장 18장까지' 계산은 1/1,891의 점추정으로, 95% 상한(0.29%)을 쓰면 3장이다 — 조사 14가 지적한 것과 같은 종류의 문제가 한 번 더 들어갔다.
4. **브라우저 구현의 '같은 규격' 근거는 Node 대조(BER 0, PDQ 거리 0, 포함도 1.000)로 충분하지만, 그것은 '같은 입력이면 같은 비트'의 증명이고 브라우저 입력이 같다는 증명은 아니다.** 다른 지점: 음원은 AudioContext 기본 표본율로 한 번 풀고 다시 5kHz로 내리는 2중 재샘플링(afp.js:96~109)이고, OfflineAudioContext 5,000Hz는 Web Audio 규격의 필수 지원 범위(8,000~96,000Hz) 밖이다 — 이 검토에서 Chromium(Playwright)으로 3,000~8,000Hz 모두 생성되는 것은 확인했으나 Firefox·Safari는 확인 못 함[추정]. 영상은 ffmpeg `fps=1`과 `currentTime` 탐색이 고르는 프레임이 다르고 YUV→RGB 변환 행렬도 다르다(거리 31 안에서 흡수되나 장면 전환 경계에서 달라짐). pdf.js↔PyMuPDF 포함도 1.000은 자작 PDF 1편·docx 1편에서만 확인됐다.
5. **발표 문구 수정안 14건을 5절 표에 정리했다.** 핵심은 "위조가 막힌다"→"무관한 내용에 옮긴 위조는 정합 단계에서 1% 수준으로 걸러진다(80건 중 0건)", "10/10"→"합성 음원 10개 중 10개(실제 음악·음성은 시험 안 함)", "같은 규격"→"같은 입력에서 비트 단위 일치, 브라우저 디코더 차이는 BER 0.006 수준(1개 확인)".

### 1.1 실험 13 (AI 공격 뒤 fingerprint, exp13_fp_after_ai.py)

**일치 확인(exp13_rows.jsonl 76행, 그림 62·사진 9·기타 5):** 이 검토에서 다시 계산한 값 — FFDNet 그림: perceptual hash 93.5%, ORB(threshold 46) 87.1%, 둘 중 하나 100%. FFDNet 사진: 100 / 88.9 / 100%. SD-VAE 그림: 91.9 / 88.7 / 95.2%. SD-VAE 사진: 100 / 88.9 / 100%. 자기 아닌 그림과 거리 ≤2인 query 5/152. 모두 일지와 같다. threshold 46은 음성(자기 제외 최고 inlier) 152개 중 ≥46이 0개, ≥45가 2개(1.3%)인 값 — 즉 '1% threshold'가 아니라 **음성 최댓값 45의 바로 위**다. 152개에서 1%는 1.5개이므로 threshold가 사실상 최댓값으로 정해지는 것은 구조적이다(조사 14 1.4절의 실험 11b와 같은 상황).

**코드 점검:**
- 참조는 원래 크기(exp13:41~42), query는 긴 변 512로 줄인 뒤 공격(48~49). ORB inlier는 아핀 RANSAC 5px(30~35), 실험 11b B의 crop 가설(격자점 90% 안쪽)은 쓰지 않음 — 일지가 '실험 11b B의 threshold 96'을 기준으로 삼은 것은 정의가 다른 점수의 비교다(B는 crop 가설 포함). 다만 결론에는 영향 없음(threshold를 이 데이터에서 다시 정했으므로).
- 자기 제외: 음성은 `j != i`로 뺌(검토 계산). 맞다.
- 동점: `enbuild2024/p13_x217`은 FFDNet·SD-VAE 모두 자기와 거리 2, 다른 그림과도 거리 2(동점). 일지 정의(자기가 '가장 가까움', ≤)로는 성공이지만 실제 조회에서는 둘 중 어느 것인지 정해지지 않는다. 동점을 빼면 FFDNet 그림 91.9%, SD-VAE 그림 90.3%(둘 중 하나는 변화 없음). 조사 14 1.1절이 지적한 '동점을 성공으로 셈'이 반복됐다.
- 5/152 오탐 중 4건이 `enbuild2024/p13_x217`, `p17_x273`(같은 논문 형제 그림), 1건이 `p18_x294` — 일지의 '형제 그림' 해석[추정]과 맞는 분포.

**지적 1 — 표의 머리글 '(threshold 46)'은 512px query 전용 값임을 표 안에 적어야 한다.** 일지 본문은 적었지만 README 표('13 | 95~100%')와 발표 표에는 조건이 없다.

### 1.2 실험 14 (SSCD 후보 생성기, exp14_sscd_candidates.py)

**일치 확인(exp14_summary.json):** 상위 1개 그림 crop 91.9/98.1%, 그림 회전 99.0/97.4%, 사진 100%; 상위 5개 전부 100%; threshold 전체 0.800·조각 0.812(음성 최댓값 0.853·0.874); 1% threshold 검출 그림 crop 36.5/57.1, 그림 회전 0.6/1.9, 사진 crop 82.2/84.4, 사진 회전 31.1/44.4%. 모두 일지와 같다.

- crop query는 `attacks.apply(... "resizedcrop")`(53행) — **조사 14가 찾은 정사각 crop 중복(tools/attacks.py:34~40, 그대로)이 그대로 들어 있다.** 실험 15 rows로 세면 그림 crop query 100개 중 55개가 중복(서로 다른 것 45개), 사진 45개 중 7개 중복. 같은 76장·같은 seed인 실험 14의 '760 query'도 서로 다른 것은 그보다 적다[추정 — 실험 15 20장에서 55% 중복이므로 76장에서도 같은 비율]. 일지의 실험 14 결과에는 이 언급이 없다(실험 15에는 있음).

### 1.5 실험 18 (그림별 key, exp18_perimage_key.py) — 3절에서 따로 다룸

**일치 확인(exp18_summary.json):** ① 평균화 → 파이프라인 0/20(z 최대 1.92, 최소 −1.34, 정확히 0.0인 것 6건) ② copy 3장 × 20 = 0/60, 후보가 그 원본인 경우 6+0+2 = 8건, '검증자가 key_i로 전체 z만 보면' 13·14·15/20(중앙값 2.53·4.55·3.09) ③ 정상 crop·회전 89/90(GEL-0009 crop 1.0에서 GEL-0008을 후보로 고름, z −0.58). 자기 key z 15.1~42.3. 모두 일지와 같다.

**코드 점검:**
- 정보 누출 없음: `estimate`·`apply_pattern`은 실험 10 함수 그대로(key 없음). 파이프라인(27~36행)은 monitor와 같은 순서.
- 위조 대상 20장(54행)은 76장 집합의 figure·photo를 3칸씩 건너 뽑은 것. 발행본 9장의 원천(FIG_SRC/…)과 같은 그림이 섞여 있으면 정합이 '맞게' 성공해 z가 커질 수 있는데, 후보·z 분포(모두 |z| < 2)로 보아 섞이지 않았다.
- **z = 0.0이 6건**: `bdct_z_valid`(tools/align.py:102~103)는 유효 블록이 하나도 없으면 0.0을 돌려준다. 이 6건은 '정합은 됐지만 되돌린 영역이 8×8 블록 하나도 못 덮음'이고, 나머지 14건은 블록이 있어서 상관을 구한 것이다. 일지의 '정합이 맞지 않아 유효 블록 z가 안 나옴'은 6건에만 맞고 14건은 **엉뚱한 변환 위에서 z를 구해 N(0,1)이 나온 것**이다.

### 1.9 실험 22 (문서 MinHash, exp22_doc_fp.py)

**일치 확인(exp22_summary.json):** 34편, threshold Jaccard 0.109(=음성 최댓값 0.109)·포함도 0.352(음성 최댓값 0.426), 복원율 표 전부, 단어 교체 포함도 최소 0.514, 20% 발췌 Jaccard 97.1%. 일지와 같다.

**코드 점검:**
- 포함도 `containment`(tools/dfp.py:49~58): 원본 bottom-512의 최댓값 `hi` 아래에 드는 질의 shingle만 보고 그중 원본에 있는 비율. hi 아래의 원본 shingle은 bottom-k에 전부 들어 있으므로 **비편향 추정**이다 — 맞다. 그러나 표본 수 = 질의 shingle 중 hi 아래인 것 ≈ |Q| × 512/|R|이고 하한이 없다. 본문 5,000 shingle인 원본에 60단어(56 shingle) 질의면 표본 약 6개 — 관용구 하나가 겹치면 0.17, 둘이면 0.33, 셋이면 0.5로 threshold를 넘는다. 실험 22의 가장 짧은 질의는 20% 발췌(≥400단어)라 **400단어 아래 질의는 시험되지 않았다.**
- Jaccard threshold 0.109 = 음성 최댓값: `np.quantile(neg, 0.99)`(76행)가 170개 음성에서 위 두 값이 같아 최댓값과 일치. 판정은 `> t`(80행)이므로 이 threshold에서 표본 내 오탐은 0%, 포함도는 1~2/170.
- 교체 단어 어휘는 처음 5편의 단어(61행) — 교체된 query가 그 5편과 조금 더 닮게 되지만 포함도 최소 0.514 ≫ 0.352라 영향 없음.
- 34편은 '본문 2,000단어 넘는 것'(56행)만 남긴 수 — 받은 PDF 전체 수는 저장소에 없다. 같은 분야(건물 에너지) 논문이라 참고문헌·관용구 공유로 음성 포함도가 0.43까지 오른 것은 일지 해석대로.
- shingle 해시를 blake2b → SHA-256으로 바꾼 뒤(27~28행) 실험 22를 다시 돌리지 않았다(일지: 추론으로 같음). MinHash·bottom-k 추정의 성질은 해시가 고르면 같으므로 맞는 추론이지만, **exp22_summary.json은 blake2b 판의 결과**라는 점을 결과 파일에 적어 두는 것이 좋다.

### 2.3 '원장 18장까지' 계산(11-14 16:45)

- 식은 Boole 상한(query 오탐 ≤ N × 쌍 오탐)으로 맞다. 쌍 오탐은 1/1,891 = 0.053%(점추정). 95% 신뢰구간은 0.0013~0.294%. 상한을 쓰면 N ≤ 0.01/0.00294 ≈ **3장**, 사이트 해시 14개의 query 오탐 상한은 14 × 0.294% ≈ **4.1%**.
- 같은 단락에서 threshold 0에는 rule of three(0/1,891의 상한 0.16%)를 썼는데 threshold 2에는 점추정을 썼다 — 한 계산 안에서 기준이 다르다. 조사 14 2.3절이 지적한 것(점추정 1% ↔ 상한 3.5%)과 같은 종류다.
- 11-15 06:39 '그림 좌우 반전 비교를 넣지 않음'(14 × 2 × 0.053% ≈ 1.5%)의 산술은 맞고 결론(안 넣음)도 보수적 방향이라 문제없다.

### 2.4 다중 비교

- 속도 탐색 11번(실험 25): 양성·음성 모두 같은 탐색을 거쳤고 음성 최소가 0.419 → 0.393으로 내려간 것을 보고했다 — 서술이 맞다. 다만 90개 순서쌍의 최소이고, 원장 음원이 늘면 '원장 수 × 11'번 비교의 최소를 쓰게 되므로 threshold 0.35와의 거리 0.04는 원장 수십 개에서 사라질 수 있다[추정 — 분포 꼬리를 모름].

## 3. 실험 18의 '위조 0/80' — 무엇을 막았고 무엇을 못 막나

**막은 것(실험으로 보인 것):** 공개 사본에서 추정한 패턴(9장 평균, 또는 1장 복사)을 **무관한 그림**에 심어 발행자 쪽 monitor 파이프라인(후보 선택 → 정합 → 후보의 key로 유효 블록 z)에 넣으면 80건 중 0건이 z > 2.326. 후보가 우연히 패턴의 원본과 같았던 8건도 넘지 않았다.

**왜 막혔나(코드로 보면):**
1. `align.candidate`(tools/align.py:54~67)는 threshold 없이 inlier 최다 원본을 **항상** 고른다(20건 모두 후보 있음).
2. `align.register`(70~93)는 좋은 짝 4개만 있으면 RANSAC 아핀을 돌려준다 — 최소 inlier 수 조건이 없다. 20건 모두 정합 '성공'(summary의 z가 모두 None 아님).
3. 무관한 내용 위의 아핀은 엉뚱한 변환이라, 되돌린 이미지의 8×8 격자는 심은 패턴과 정렬되지 않는다 → z ~ N(0,1). 유효 블록이 없으면 0.0(6건).
→ 즉 보호의 실체는 **'내용이 안 맞으면 패턴이 격자에 정렬되지 않는다'**이고, 그 귀결은 1% 오탐의 통계 검정이다. 80번 시도에 0.8번은 넘을 수 있다(관측 0건은 이와 일치, 상한 4.5%).

**그림별 key의 역할은 분리해서 재지 않았다:**
- 실험 10의 20/20은 **전체 이미지 z, 단일 key, 파이프라인 없음**. 실험 18 ①의 0/20은 **파이프라인 있음, 그림별 key**. 두 변수가 동시에 바뀌어 '같은 key면 20/20 → 그림별 key면 0/20'은 비교가 아니다. 같은 key라도 파이프라인을 거치면 무관한 그림에서는 같은 이유로 0에 가까웠을 것이다[추정 — 정합이 내용으로 결정되므로].
- 그림별 key만의 효과를 보려면 ②에서 한 것처럼 ①에도 `W.score(f, key_i)`(각 i)를 기록해야 한다(exp18:61~63에 없음). 실험 10 데이터(exp10_summary.json)로 외삽하면: 한 장에서 추정한 패턴의 부호 일치율은 K=1에서 평균 60.7%(위조 z 중앙값 2.29), K=9에서 60.6%(z 중앙값 5.06) — z는 '일치율 초과분(2p−1)'에 비례하고 그 비례상수는 약 24. 그림별 key로 심은 9장을 평균하면 추정 패턴은 9개 독립 패턴의 합이므로 각 key_i와의 상관은 단일 패턴일 때의 약 1/√9 = 1/3(가우시안 근사; 부호 합 모형으로는 0.27/0.5 ≈ 0.55배)로 줄어 전체 이미지 z ≈ 24 × 0.107 × (1/3 ~ 0.55) ≈ **1.4~1.7** + N(0,1). 즉 **그림별 key만으로는 평균화 위조의 전체 이미지 z가 2.326을 넘는 경우가 20장 중 약 20~27%(정규 근사) 있을 수 있다**[계산 — 선형 외삽]. key 수가 많아질수록 0으로 가지만 9개는 많지 않다. `W.score` 20 × 9번의 작은 계산으로 확정할 수 있다.

**못 막는 것(발표에서 같이 말해야 함):**
1. **copy attack의 본래 위험**: 원본 i와 **내용이 맞는** 대상(원본 i를 고쳐 만든 그림 — 숫자를 바꾼 그래프, 결론을 바꾼 도식)에 패턴을 옮기면 정합이 맞게 성공하고 key_i로 검정되어 '연구실 그림'으로 읽힌다. 실제로는 패턴을 옮길 필요도 없다 — 원본 파일을 고치면 워터마크가 그대로 남아 있다. **워터마크(와 정합)는 '우리 그림에서 나왔다'를 말하고 '고치지 않았다'는 말하지 않는다.** 고치지 않았다는 것은 C2PA/해시의 일이다. 실험 18에는 이 경우가 없다(대상 20장이 모두 무관한 그림).
2. TrustMark는 공개 모델이라 누구나 'GEL-0008'을 아무 그림에 심을 수 있다 — monitor는 '워터마크 단서만(위조 가능)'으로 표시한다(1.11절). 그림별 key는 block DCT에만 해당.
3. 1% 검정이므로 공격자가 대상 그림을 수백 장 바꿔 가며 시도하면 몇 장은 넘는다. '0건'은 '불가능'이 아니다.
4. 브라우저 검증 페이지는 block DCT를 검정하지 않으므로(key가 서버/발행자에만 있음) 이 보호는 **발행자 쪽 monitor에만** 있다. '참고' 행(13~15/20)은 'key를 가진 검증자가 원장 대조 없이 전체 z만 보면' 당하는 경우이고, 지금 구조에서 그런 검증자는 monitor 자신뿐이다.
5. 표본: 발행본 9장, 대상 20장, copy 원본 3장. 추정기는 실험 10의 것 하나.

**정상 검출 89/90**은 그림 9장 × (crop 5 + 회전 5)이고 crop 5단계는 중복이 있다(1.2절) — 서로 다른 query 수는 90보다 적다.

## 4. 브라우저 구현 — 'Python과 같은 규격' 주장의 근거와 달라질 수 있는 지점

### 4.1 근거가 충분한 부분(코드 대조)

- **afp.js ↔ afp.py:** 창 함수(numpy.hanning 식, afp.js:6), 대역 경계(geomspace와 같은 식, 7~17행), 프레임 수·비트 규칙(46~66 ↔ afp.py:35~42), BER의 ±8 이동(68~79 ↔ 45~54), 원장 비트 순서(82~93, big-endian ↔ np.packbits 기본) 모두 같다. Node 대조 BER 0.0000(일지)과 일치하는 구조.
- **pdq.js ↔ pdqhash:** 휘도 계수 0.299/0.587/0.114, Jarosz 상자 필터의 4단계(box1D 5~13행), 창 크기 식(15행), 2회 반복(27~30), 솎아내기 `(i+0.5)·rows/64`(33~34), 품질(37~39, 정수 절단 포함), DCT 행렬(17~21, 직류 제외), 중앙값 sorted[127](45), 비트 역순(47)이 pdq/cpp 순서와 같다. Node 5장 거리 0.
- **dfp.js ↔ dfp.py:** 단어 정규식·소문자(5~7 ↔ 21~22), SHA-256 앞 8바이트 >>3(9~18 ↔ 25~29), 포함도(21~28 ↔ 49~58), docx 문단 정규식(47~50 ↔ 61~67) 같다. 차이: Python `html.unescape`는 모든 엔티티, JS는 5종 + `&#39;`(49행) — 숫자 엔티티(`&#8217;` 등)가 들어간 docx에서 단어가 갈릴 수 있으나 단어 정규식이 기호를 버리므로 shingle 영향은 작다[추정].

### 4.3 정리

'같은 규격'의 근거는 **같은 5kHz 신호 / 같은 RGB 프레임 / 같은 텍스트가 들어가면 같은 비트**라는 것까지이고 Node 대조가 그것을 보였다. 브라우저에서 입력을 만드는 단계(디코더·재샘플러·프레임 탐색·pdf.js)는 배포 사이트에서 **형식마다 샘플 1개**로 확인됐다. 발표에서는 "비트 단위로 같은 규격(Node 대조), 브라우저 디코더 차이는 샘플에서 BER 0.006 수준"처럼 두 층을 나눠 말하면 정확하다.

## 7. 코드 지적 모음(파일:줄)
