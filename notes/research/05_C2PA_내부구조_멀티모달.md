# 기술조사 05 — C2PA의 내부 구조와 멀티모달(영상·음원·문서) 적용

> 작성 2026-11-13(금) 16:00~16:50 KST, 자동 조사. 기준 규격: C2PA 기술 규격 2.4(2026-04). 다음 방문(2026-11-17 화) 전 읽기용.

**요약(5줄)**
1. 우리 서명 PNG를 직접 열어 보니 구조는 `caBX` 청크 1개 → JUMBF 상자 트리(매니페스트 → assertion 저장소·claim.v2·COSE 서명)이며, 매니페스트 100,285바이트 중 썸네일이 86KB, 서명 상자(인증서 2장·TSA 토큰 6KB 포함)가 12KB다.
2. 엄격한 결속은 형식별로 세 가지다. PNG·JPEG·WAV·MP3·PDF는 "바이트 범위 해시(`c2pa.hash.data`, 매니페스트 자리만 제외)" 또는 "상자별 해시(`c2pa.hash.boxes`)", MP4·MOV는 "BMFF 상자 해시(`c2pa.hash.bmff.v3`, 조각 영상은 머클 트리)". 어느 쪽이든 픽셀·샘플이 1바이트만 바뀌어도 깨지고, 메타데이터만 고쳐도 대부분 깨진다. 우리 PNG는 규격이 권장(should)하는 상자 해시가 아니라 바이트 범위 해시로 서명돼 있다.
3. 느슨한 결속(`c2pa.soft-binding`, 규격 18.10)은 "알고리즘 이름 + 값(워터마크 ID 또는 핑거프린트) + 범위(영역/시간 구간)"의 CBOR이며, 등록 목록에는 2026-10-28 기준 60개 알고리즘(TrustMark Q/C/P/F 포함)이 있다. 되찾기는 Soft Binding API(`GET /matches/byBinding` → `GET /manifests/{id}`)로 한다. c2pa-python 0.38은 이 assertion을 JSON으로 그대로 받는다(파싱 확인, 서명은 키가 없어 미실행).
4. 신뢰 검증은 "인증서 체인이 검증기의 신뢰 목록에 닿는가(14.4·15.7) + 폐기 안 됐는가(OCSP, 15.9; CRL 금지 14.5.2) + 서명 시각을 TSA가 증언하는가(15.8)"의 세 겹이며, 우리 파일은 체인·TSA 모두 유효하지만 둘 다 '신뢰 목록 밖'이라 `signingCredential.untrusted`·`timeStamp.untrusted`가 난다. 서명 인증서는 규격이 요구하는 digitalSignature 키 사용·비어 있지 않은 EKU(이메일 보호)를 충족한다.
5. 멀티모달: 설치된 c2pa-python 0.38(c2pa-rs 0.91)로 **MP4·MOV·WAV·MP3·FLAC는 읽기·쓰기 모두 가능**, **PDF는 읽기만**(쓰기 목록에 없음), **텍스트는 없음**(Rust 비공개 기능). 조각 영상(DASH)은 Rust 라이브러리 파일 API만 지원. 3단계 계획: ① 음원(WAV)·영상(MP4) 서명을 지금 코드로 즉시 확장 → ② soft-binding assertion과 원장 조회를 Soft Binding API 형태로 정리 → ③ PDF는 외부 도구·사이드카로 우회하며 Rust 쪽 쓰기 지원을 추적.

용어 풀이는 처음 나올 때 괄호로 단다. [확인]은 규격·코드·실행으로 확인한 사실, [추정]은 내 해석이다. 값마다 "무엇을 — 왜"와 출처(규격 절 번호 또는 URL)를 단다. 출처 없는 값은 '확인 못 함'으로 적는다.

## 1. 매니페스트 구조 — 우리 서명 파일을 실제로 열어 본 결과

### 1.1 도구와 방법 [확인]
- `c2pa-python` 0.38.0(내부 c2pa-rs 0.91.0)을 이 클라우드 세션의 임시 가상환경에 설치해 `docs/assets/signed/buildings2026-01.png`를 `Reader`로 읽고, 별도로 PNG 청크와 JUMBF 상자를 바이트 단위로 파싱(직접 짠 60줄짜리 스크립트, `cbor2`로 CBOR 해독)했다. `c2patool`은 설치하지 않았다(Rust 바이너리 내려받기 생략, Python으로 같은 정보가 나옴).
- 저장소 파일은 읽기만 했고 수정하지 않았다. 개인키는 쓰지 않았다.

### 1.2 전체 모양 [확인]

```
PNG 시그니처(8B) → IHDR → caBX(100,285B) → IDAT×17 → IEND         (파일 1,156,314B)
caBX 안:
jumb  c2pa                                   ← 매니페스트 저장소(Manifest Store)
 └ jumb  urn:c2pa:dc7ff7f7-…-24ea7ca2e86c    ← 매니페스트 1개 (URN이 상자 라벨)
     ├ jumb c2pa.assertions                  ← assertion 저장소 (87,086B)
     │   ├ jumb c2pa.thumbnail.claim  (bfdb 20B + bidb 86,349B = JPEG 썸네일)
     │   ├ jumb c2pa.actions.v2       (cbor 322B)
     │   └ jumb c2pa.hash.data        (cbor 123B)   ← 엄격한 결속
     ├ jumb c2pa.claim.v2             (cbor 692B)   ← claim
     └ jumb c2pa.signature            (cbor 12,283B) ← COSE_Sign1
```

용어:
- **JUMBF**(JPEG Universal Metadata Box Format, ISO/IEC 19566-5): "길이(4B)+종류(4B)+내용"으로 된 상자를 겹겹이 담는 포장 규격. C2PA는 모든 구성요소를 이 상자로 싼다(규격 2.4 §10.1 및 부록 A). 각 `jumb` 상자의 첫 자식 `jumd`(설명 상자)에 16바이트 종류 UUID와 문자열 라벨이 들어 있어서 위 트리의 이름이 나온다.
- **매니페스트 저장소**: 라벨 `c2pa`인 최상위 상자. 매니페스트가 여러 개면 여기에 나란히 들어가고, 가장 최근 것이 활성 매니페스트다(규격 §10.2, 활성 매니페스트는 Reader의 `active_manifest`로 나옴).
- **assertion(주장)**: "이 파일은 이렇게 만들어졐다"는 개별 진술. 우리는 행동(actions), 썸네일, 데이터 해시 세 개.
- **claim(주장 묶음)**: assertion들의 **해시 목록**과 서명자 정보. 우리 claim.v2의 내용:
  - `created_assertions`: `c2pa.hash.data`(해시 32B) — 서명자가 직접 만든 것
  - `gathered_assertions`: `c2pa.thumbnail.claim`, `c2pa.actions.v2` — 모아 온 것(규격 §10.3.2: created 쪽만 서명자 책임으로 귀속됨 §9.2.6)
  - `instanceID` xmp.iid:…, `claim_generator_info` {lab-provenance 0.1.0, org.contentauth.c2pa_rs 0.91.0}, `dc:title`, `alg` sha256, `signature` → 서명 상자 URI
- **ingredient(재료)**: 부모·구성 요소 파일의 매니페스트를 가리키는 assertion(§18.16). 우리 파일에는 **없음**(새로 만든 것으로 서명했기 때문). 관계는 `parentOf`·`componentOf`·`inputTo` 셋(§18.16.3).
- **서명(COSE_Sign1_Tagged, RFC 9052)**: 규격은 모든 서명을 이 구조로 하라고 한다(§13.2.2). 우리 서명을 풀어 보면:
  - 보호 헤더: `alg = -7`(ES256), `x5chain(라벨 33)` = 인증서 2장(서명용 599B, 발급 기관 580B). 규격 §14.5: x5chain은 보호 헤더에만, 루트는 **넣지 않는 것이 좋다(should not)** → 우리 파일도 루트 없이 2장. 일치.
  - 페이로드: 없음(detached). 서명 대상은 claim 상자의 바이트(§13.2.2).
  - 비보호 헤더: `sigTst2`(RFC 3161 타임스탬프 토큰 5,998B 1개)와 `pad`(4,970B 0바이트). 규격 §10.3.2.5: 2.x 타임스탬프는 `sigTst2`, 매니페스트당 1개.
  - 서명값 64B(ECDSA P-256).
- **타임스탬프 토큰 내용**(openssl ts로 해독): 시각 2026-11-13 03:38:41 UTC, 해시 sha256, 정책 OID 2.16.840.1.114412.7.1(DigiCert), nonce 있음. 서명 시각(`signature_info.time`)과 같은 초.

### 1.3 용량 분해 [확인]
| 구성 | 바이트 | 비율(매니페스트 100,285B 기준) |
|---|---|---|
| 썸네일 JPEG(`c2pa.thumbnail.claim`) | 86,447 | 86% |
| COSE 서명 상자(인증서 2장 1.2KB + TSA 토큰 6.0KB + pad 5.0KB + 나머지) | 12,331 | 12% |
| claim.v2 | 739 | 0.7% |
| actions.v2 + hash.data | 590 | 0.6% |

개발일지의 "+99KB" 관찰은 이렇게 설명된다. **썸네일을 끄면 매니페스트가 14KB 수준으로 준다**[확인: 위 합산]. c2pa-rs는 Builder 설정으로 썸네일 생성을 끌 수 있다(`Settings` `builder.thumbnail.enabled`, c2pa-rs 설정 문서; 우리 `tools/sign.py`는 기본값이라 켜져 있음). 썸네일을 끄는 것이 좋은지는 용도에 따른 결정이라 여기선 값만 적는다.

### 1.4 검증 결과 코드(Reader `validation_results`) [확인]
- 성공: `timeStamp.validated`, `claimSignature.insideValidity`, `claimSignature.validated`, `assertion.hashedURI.match`×3, `assertion.dataHash.match`
- 정보: `signingCredential.ocsp.skipped`(인증서에 OCSP 주소가 없으니 건너뜀), `timeStamp.untrusted`(DigiCert TSA가 이 검증기의 TSA 신뢰 목록에 없음)

코드의 뜻은 규격 §15.2.2(성공 §15.2.2.1, 정보·실패 §15.2.2.2).

## 2. 엄격한 결속(hard binding) — 형식별로 해시가 덮는 것과 빼는 것

**용어**: 엄격한 결속 = "이 매니페스트가 바로 이 파일의 것이고 파일이 바뀌지 않았다"를 보증하는 해시(§9.1). 매니페스트당 **정확히 1개**(§10.2.2·§11.2.2, 0개면 `claim.hardBindings.missing`, 2개 이상이면 `assertion.multipleHardBindings` §15.10.1). 종류는 다섯: `c2pa.hash.data`, `c2pa.hash.boxes`, `c2pa.hash.bmff.v3`(v2는 폐기), `c2pa.hash.collection.data`, `c2pa.hash.multi-asset`(§11.2.2, §18.4 표 7). 해시 알고리즘은 SHA2-256/384/512만(§13.1).

### 2.1 세 가지 방식 [확인]
| 방식 | 라벨 | 덮는 것 | 빼는 것 | 규격 |
|---|---|---|---|---|
| 바이트 범위 해시 | `c2pa.hash.data` | 파일 전체 바이트(0~끝) | `exclusions` 배열의 (start, length) 구간. 원칙상 **매니페스트 저장소와 자산 메타데이터만** 제외 가능. 그 외 제외가 있으면 정보 코드 `assertion.dataHash.additionalExclusionsPresent` | §9.2.1, §18.5, §15.12.1.1 |
| 상자별 해시 | `c2pa.hash.boxes` | 상자(PNG 청크·JPEG 세그먼트 등)를 **파일에 나오는 순서대로** 이름과 해시로 나열. 묶어 적은 상자들은 사이 바이트까지 포함 | C2PA 상자는 이름 `C2PA`, 해시 `00` 한 바이트로 따로 둠. 목록에 없는 상자가 있거나 순서가 다르면 실패(`assertion.boxesHash.unknownBox`/`mismatch`) | §9.2.2, §18.7 |
| BMFF 상자 해시 | `c2pa.hash.bmff.v3` | MP4·MOV·HEIF·AVIF의 상자 트리. 통짜 MP4는 `mdat`를 한 덩이로, 조각 MP4는 조각별 해시를 **머클 트리**(`merkle` 필드: uniqueId·localId·count·hashes·initHash)로 | `exclusions`(xpath로 상자 지정, 필수)에 **C2PA uuid 상자·`ftyp`·`mfra`는 항상** 제외 | §9.2.3, §18.6, 부록 A.5 |

- `pad`/`pad2`(0으로 채운 바이트): 해시를 먼저 계산하고 매니페스트 길이가 바뀌어도 오프셋이 안 밀리도록 자리를 잡아 두는 것. 검증기는 **무시해야 한다**(§15.12.1.1). 우리 hash.data의 pad는 6B, COSE 헤더의 pad는 4,970B.
- 규격의 권고 방향: 바이트 범위 해시는 "상자 구조가 없는 형식에만 고려(should only be considered)", JPEG·PNG·GIF 같은 상자형은 **상자별 해시를 써야(should)** 한다(§9.2.1·§9.2.2). **그러나 우리 PNG는 `c2pa.hash.data`로 서명되어 있다**(c2pa-rs 기본 동작). 규격 위반은 아니고(두 가지 모두 허용) 권고와 다른 것이다[확인].

### 2.2 우리 PNG의 실제 값 [확인]
```
c2pa.hash.data = { exclusions:[{start:33, length:100285}], alg:"sha256", hash:<32B>, pad:<6B 0x00>, name:"jumbf manifest" }
```
- start 33 = 시그니처 8B + IHDR 청크(4+4+13+4=25B) 바로 다음, 즉 caBX 청크의 길이 필드부터. length 100,285 = caBX 청크 전체(길이 4 + 종류 4 + 내용 100,273 + CRC 4). **→ 제외 범위는 caBX 청크 하나뿐이고 나머지 바이트(IHDR, IDAT 전부, IEND)는 모두 해시에 들어간다.**
- 그래서 개발일지의 "픽셀 1바이트 바꾼 그림 → `assertion.dataHash.mismatch`"가 나온다. 같은 이유로 **PNG를 다시 저장(재압축, 청크 순서 변경, tEXt 추가)해도 깨진다**[추정: IDAT 바이트열이 바뀌므로; 개발일지 "다시 저장한 그림 → 증명서 없음"은 PIL이 caBX를 버려서 생긴 더 앞 단계 결과].

### 2.3 형식별 삽입 위치와 결속 방식 [확인: 규격 2.4 부록 A]
| 형식 | 매니페스트가 들어가는 자리 | 쓰는 결속 | 어떤 편집에 깨지는가 [추정, 해시 범위에서 유도] |
|---|---|---|---|
| **PNG** | 비공개 보조 청크 `caBX`, IDAT 앞 권장(A.3.2) | hash.data(c2pa-rs 기본) 또는 hash.boxes | 픽셀 변경·재압축·다른 청크 추가/삭제·청크 순서 변경 전부. 메타데이터만 바꿔도 깨짐(제외 구간이 caBX 하나이므로) |
| **JPEG** | `APP11` 마커 세그먼트에 JUMBF, 길면 여러 세그먼트로 분할·연속(A.3.1) | hash.data 또는 hash.boxes(규격 권장) | 재인코딩(품질 변경), 리사이즈, EXIF/XMP 수정, 썸네일 재생성. hash.boxes로 하고 EXIF 세그먼트를 `excluded:true`로 두면 메타데이터 수정은 살릴 수 있음(§18.7) |
| **MP4/MOV**(BMFF) | `uuid` 상자(확장 타입 D8FEC3D6-1B0E-483C-9297-5828877EC481), `ftyp` 뒤·첫 `mdat`·`moov` 앞(A.5) | **hash.bmff.v3 필수**(§11.2.2, A.5). ftyp·mfra·C2PA uuid 제외 | 재인코딩·트랜스코딩·트리밍·오디오 트랙 교체. **`moov`(메타데이터 상자) 수정도 깨짐**(제외 목록에 없으면). ftyp 교체(브랜드 변경)·mfra 재생성은 살아남음 |
| **조각 MP4(DASH/HLS, fMP4)** | 초기화 세그먼트의 `uuid` 상자에 매니페스트, `moov`를 덮는 bmff 해시. 미디어 세그먼트별 해시는 머클 트리(§19.2.3, §18.6 merkle) | hash.bmff.v3 + merkle. 라이브는 ① 세그먼트마다 매니페스트 상자(§19.3) 또는 ② `emsg` 상자에 세션 키로 서명한 세그먼트 정보(§19.4) | 세그먼트 하나라도 재패키징·재암호화되면 그 조각만 실패(아직 안 받은 조각은 실패 아님 §15.12.2). 플레이어가 조각을 합쳐 MP4로 저장하면 구조가 바뀌어 깨짐 |
| **WAV/AVI/WebP**(RIFF) | 첫 RIFF 헤더 청크의 **마지막 하위 청크**로 `C2PA` 청크(A.3.7) | hash.data(c2pa-rs) 또는 hash.boxes | 샘플 편집·리샘플링·포맷 변환(→MP3)·`LIST/INFO` 메타데이터 수정·청크 재배열 |
| **MP3/FLAC**(ID3) | ID3v2 `GEOB`(일반 캡슐화 객체) 프레임, MIME은 JUMBF 타입(A.3.4) | hash.data | 재인코딩(비트레이트 변경), ID3 태그 편집(제외 안 하면), 앨범아트 추가. 스트리밍 플랫폼 업로드 시 ID3 재작성이 흔하므로 **소실 가능성 큼**[추정] |
| **PDF** | 임베디드 파일 스트림(Subtype `application/c2pa`, `AFRelationship` `C2PA_Manifest`), 카탈로그 `/AF`와 EmbeddedFiles 이름 트리 또는 `FileAttachment` 주석으로 참조(A.4) | **hash.data**, PDF 전자서명이 있으면 그 `/Contents` 구간을 exclusions에 추가(A.4) | 증분 저장(incremental update)은 규격이 "앞 매니페스트 = 초기, 최신 = 활성"으로 다루므로 정당한 편집 체인은 가능. 그 외 재저장·최적화·주석 추가·메타데이터 수정은 깨짐. 인증 서명(DocMDP)이 P=3일 때만 주석 방식으로 추가 가능 |
| **텍스트(비구조)** | 글 끝에 U+FEFF + 유니코드 변이 선택자(Variation Selector) 열로 인코딩한 `C2PATextManifestWrapper`(A.8) | hash.data, **NFC 정규화한 UTF-8** 기준 바이트 오프셋 | 한 글자라도 바뀌면 깨짐. 복사·붙이기에서 변이 선택자가 제거되면 매니페스트 자체가 사라짐 |
| **구조 텍스트(코드·설정·마크업)** | `-----BEGIN C2PA MANIFEST-----`~`END` 블록을 주석 줄 또는 front matter에(A.9) | hash.data, 블록 하나를 제외 | 포매터·린터가 공백만 바꿔도 깨짐 |
| **ZIP 계열(DOCX·PPTX·EPUB·ODF)** | `META-INF/content_credential.c2pa`, 비압축(A.6) | **hash.collection.data**: 아카이브 안 파일마다 전체 바이트 해시 + `zip_central_directory_hash`(§18.8) | 아무 구성 파일 하나라도 바뀌면 깨짐. 단 **목록에 없는 파일을 추가하는 것은 못 막는다**(§18.8 주의 문구) |
| **HTML** | `<script type="application/c2pa">`(Base64) 또는 권장 `<link rel="c2pa-manifest">`(A.7) | hash.data(script 요소 제외) | 어떤 편집에도 깨짐 |
| **SVG** | `<metadata>` 안 `c2pa:manifest` 요소에 Base64, 외부 매니페스트 권장(A.3.3) | hash.data | 어떤 편집에도 깨짐 |

이 표의 "어떤 편집에 깨지는가" 열은 **규격의 해시 범위 정의에서 논리적으로 유도한 것**이고 직접 실험한 것은 PNG 픽셀 1바이트 변경만이다(개발일지). 사용자 규칙("생각만으로 아는 비교는 실험하지 않는다")에 따라 실험 대신 근거를 적었다.

## 3. 느슨한 결속(soft binding) — 규격 2.4의 형식과 실제 넣는 방법

(규격 조문 위주의 개요는 보고서 02의 3.2절에 있다. 여기선 **데이터 형식·알고리즘 목록·API·코드**만 다룬다.)

### 3.1 assertion 형식 [확인: §18.10]
라벨 `c2pa.soft-binding`, CBOR. 한 매니페스트에 0개 이상(§9.1).
```
soft-binding-map = {
  alg:        tstr,                 ; 필수. 알고리즘 이름+버전. 알고리즘 목록에 있어야 "함"(2.4에서 shall→should로 완화 §9.3.2, 변경 이력)
  blocks:     [+ soft-binding-block-map], ; 필수. 값이 적용되는 구간들
  ? alg-params: bstr,               ; 알고리즘별 CBOR 매개변수
  ? name: tstr, ? pad: bstr, ? pad2: bstr,
  ? bindingMetadata: { ? description, ? contact, ? informationalUrl, * },  ; 검증에 쓰지 말 것(should not)
  ? url: uri                        ; 폐기. 생성기는 넣지 말 것(shall not)
}
soft-binding-block-map = {
  scope: { ? timespan: {start: uint, end: uint},   ; 밀리초, 미디어 시작 기준 → 음원·영상
           ? region: region-map,                  ; §18.2 영역 → 이미지·영상 공간
           ? extent: bstr },                      ; 폐기
  value: bstr                                     ; 알고리즘별 값(워터마크로 복원한 ID, 또는 핑거프린트)
}
```
- 그림 하나 전체에 붙일 때는 `scope: {}`(빈 맵)으로 두면 된다[추정: 규격은 region·timespan 모두 선택 사항이라 적음; c2pa-rs `SoftBindingScope`도 두 필드 모두 Option].
- 느슨한 결속으로 **되찾아 온 매니페스트를 재료로 넣을 때**는 ingredient에 `softBindingsMatched: true`와 `softBindingAlgorithmsMatched: [알고리즘]`을 적는다(§18.16.14).

### 3.2 등록 알고리즘 목록 [확인: c2pa-org/softbinding-algorithm-list, `softbinding-algorithm-list.json`, 2026-11-13 조회]
- 총 **60개**(번호 1~61, 59번 빠짐). 워터마크가 다수, 핑거프린트 11개.
- 우리와 직접 관련: `com.adobe.trustmark.Q` / `.C` / `.P` / `.F`(이미지 워터마크, Adobe) — 우리가 쓰는 TrustMark 라이브러리의 변종 Q·C·P가 모두 등록돼 있고 F는 2026-10-14 추가. 우리 블록 DCT 워터마크는 등록돼 있지 않다 → `alg`에 쓸 공식 이름이 없다(2.4부터 should라 넣을 수는 있으나 남이 해석 못 함).
- 핑거프린트 쪽: `io.iscc.v0`(ISO 24138, 텍스트·이미지·음원·영상 모두), `com.adobe.icn.dense`(이미지), `ai.trufo.pawprint.fingerprint`, `com.digicaps.fingerprint.1`(한국 DigiCAP, 이미지), `com.evixar.efp.type3.1`(음원·영상), `com.joinmonolith.sha256`(모든 형식), WritersLogic 텍스트 핑거프린트 3종, `com.encypher.text.fingerprint.1`. **우리 lab-phash·PDQ·ORB는 등록된 이름이 없다.**
- 멀티모달에 쓸 수 있는 등록 워터마크(음원·영상 포함): `com.digimarc.validate.1`(음원·영상·텍스트·이미지), `com.microsoft.wavmark.1`(음원·영상, 공개 논문 arXiv 2308.12770), `com.aiwatermark.audioseal.1`(Meta AudioSeal 계열 이름, WAV·MP3·FLAC), `com.adobe.hiermark.A`(음원), `com.adobe.flowmark.A`(영상), `com.markany.watermark.1`(한국 MarkAny, 이미지·영상·음원), `com.doverunner.watermark.1`(영상), `studio.aidr.silentcipher.1`(WAV). 텍스트 워터마크: WritersLogic `zwc-watermark`(제로폭 문자), `com.cognitive-proof.vsrmark.1`, `com.encypher.text.watermark.1`.
- 목록 항목 형식: `alg`, 종류, `decodedMediaTypes`(또는 `encodedMediaTypes` MIME), 연락처, URL, 등록일(스키마 `softbinding-algorithm-list-schema.json`).

### 3.3 증명서 되찾기 API(Soft Binding Resolution API) [확인: spec.c2pa.org …/2.4/softbinding/Decoupled.html, OpenAPI 2.3.0]
| 단계 | 호출 | 내용 |
|---|---|---|
| 조회 | `GET /matches/byBinding?alg=&value=(base64)&maxResults=` 또는 `POST /matches/byBinding`(큰 값) | 워터마크 ID·핑거프린트 값으로 질의. 응답 `matches[]` = {`manifestId`(필수), `endpoint`(선택), `similarityScore` 0~100} |
| 조회(파일 업로드) | `POST /matches/byContent`, `POST /matches/byReference`(HTTPS URL, assetLength, assetType, region) | 저장소가 직접 결속값을 계산 |
| 가져오기 | `GET /manifests/{manifestId}?returnActiveManifest=` | 매니페스트 저장소(.c2pa) 또는 활성 매니페스트만 |
| 저장 | `POST /manifests`, `POST|PUT /bindings`, `DELETE /manifests/{id}`; `GET|POST /manifests/{id}/receipts`(접수 영수증) | 발행 측 |
| 서비스 | `GET /services/supportedAlgorithms` | 지원 알고리즘 |
| 인증 | OAuth 2.0 client credentials, 스코프 `fetch:manifests`, `store:manifests`, `store:bindings`(조회는 무인증도 허용 가능) | |
- 우리 `verify.js`의 "원장 조회"(lab-phash 해밍 거리 ≤15로 ledger.jsonl 검색 → 원래 매니페스트 ID)는 이 API의 `byBinding`+`manifests/{id}`를 정적 파일 하나로 흉내 낸 것이다[확인: verify.js 71~97행]. 차이: 알고리즘 이름이 등록돼 있지 않고, 유사도 점수·엔드포인트 개념이 없고, 매니페스트 원본(.c2pa 바이트)을 돌려주지 않는다.
- 문서 2장 "Federated Lookup"(여러 저장소 연합 조회, 키-값 저장 스키마)은 본문이 잘려 **확인 못 함**.

### 3.4 c2pa-rs / c2pa-python에서 넣는 방법 [확인: 코드·문서, 서명 실행은 안 함]
- Rust: `c2pa::assertions::SoftBinding { alg: Option<String>, blocks: Vec<SoftBindingBlock{scope: SoftBindingScope{timespan, region}, value: Vec<u8>}>, name, alg_params, binding_metadata }`, 라벨 상수 `SoftBinding::LABEL`. 생성자 없음(필드 공개, `Default`). `Builder::add_assertion("c2pa.soft-binding", &sb)`(docs.rs c2pa 0.92.1 Builder). `value`·`pad`는 serde_bytes라 JSON에서는 base64 문자열 또는 정수 배열로 넘기면 내부 `soft_binding_bytes_to_bstr`가 CBOR bstr로 바꾼다(sdk/src/assertions/soft_binding.rs).
- Python(0.38.0): 별도 클래스 없음(패키지 안에 soft-binding 심볼 0건[확인: grep]). 매니페스트 JSON의 `assertions`에 그대로 적으면 된다. 아래 JSON을 `Builder(json, ctx)`에 넣었을 때 **파싱 단계는 통과**했다(이 세션에서 실행). 서명까지의 통과는 키가 없어 **확인 못 함**(개인키를 만들지 않는 규칙).
```json
{"label": "c2pa.soft-binding",
 "data": {"alg": "com.adobe.trustmark.Q",
          "blocks": [{"scope": {}, "value": "AAECAwQFBgcICQ=="}]}}
```
  - `alg` 값으로 `com.adobe.trustmark.Q`를 든 이유: 우리가 TrustMark Q 변종으로 실험했고(개발일지) 목록에 등록돼 있어 남의 검증기가 해석할 수 있는 유일한 우리 알고리즘이기 때문. `value`는 TrustMark가 복원하는 비트열(Q 변종 BCH 방식에 따라 페이로드 길이가 다름 — 우리 실험 설정값은 개발일지 참조)을 바이트로 적는다[추정: 규격은 "알고리즘별 값"이라고만 함].
- 썸네일·행동 등 다른 assertion과 같은 방식이므로 `tools/sign.py`의 `manifest()` 딕셔너리에 항목 하나를 추가하면 끝이다(이번에는 파일을 수정하지 않았다).
- Adobe 쪽 통합 사례: Content Authenticity 앱이 TrustMark 워터마크 + 클라우드 매니페스트 저장소로 "Durable Content Credentials"를 구현(개발일지 11-13 조사, contentauthenticity.org 블로그). TrustMark 저장소 README가 C2PA soft binding 라벨 사용을 안내하는지는 이번에 **확인 못 함**.

## 4. 신뢰 검증 세부

### 4.1 서명 인증서 조건 [확인: §13.2.1, §14.5.1.1]
| 조건 | 규격 | 우리 서명용 인증서(openssl로 해독) |
|---|---|---|
| X.509 v3 | §14.5.1.1 | v3 |
| 서명 알고리즘: ES256/384/512, PS256/384/512(RSA ≥2048), EdDSA(Ed25519만) | §13.2.1 | ES256(ecdsa-with-SHA256, P-256) |
| 허용 곡선 P-256/384/521 | §14.5.1.1 | P-256 |
| Key Usage에 **digitalSignature** 비트 | §14.5.1.1 | Digital Signature(critical) |
| **EKU 확장이 있고 비어 있지 않아야**(end-entity) | §14.5.1.1 | id-kp-emailProtection(1.3.6.1.5.5.7.3.4) |
| timeStamping·OCSPSigning EKU가 있으면 그 하나만 | §14.5.1.1 | 해당 없음 |
| Basic Constraints CA=false | 일반 PKI 관행(규격 절 번호 확인 못 함) | CA:FALSE(critical) |
| x5chain은 보호 헤더, 루트 제외 | §14.5 | 보호 헤더, 2장(루트 없음) |
| 폐기 확인 수단: **CRL 금지**, OCSP 권장, 응답을 `rVals` 비보호 헤더에 스테이플 | §14.5.2 | 인증서에 AIA/OCSP 주소 없음 → `ocsp.skipped` |
- 검증기는 **EKU별로 신뢰 앵커 목록을 따로** 둔다(§14.4.1: "C2PA claim-signing EKU" 포함). 어떤 EKU를 받아 줄지는 검증기 설정이다. c2pa-rs 기본 설정은 emailProtection·documentSigning 등을 허용 목록으로 가짐[추정: c2pa-rs `trust.allowed_list`·EKU 설정이 있다는 것은 알지만 기본값 문자열은 이번에 확인 못 함].

### 4.2 검증 순서와 신뢰 [확인: §15.7~15.9]
1. **타임스탬프 먼저**(§15.7): 유효한 타임스탬프가 있으면 그 시각을 "지금"으로 삼아 인증서 유효기간을 본다(§15.8 "attested time, not the current time"). 없으면 현재 시각이 서명 인증서 유효기간 안이어야 하고, 아니면 `claimSignature.outsideValidity`로 거부. → **타임스탬프의 역할 = 인증서가 만료·폐기된 뒤에도 "서명 당시엔 유효했다"를 증명**하는 것. 우리 인증서는 2027-11-12 만료이므로 그 뒤에도 TSA 덕에 유효 판정이 가능하다[확인: 토큰 시각 2026-11-13 03:38:41Z].
2. TSA 인증서도 **별도의 TSA 신뢰 목록**에 닿아야 하고(§14.4.2, §15.8 "C2PA TSA Trust List"), 못 닿으면 `timeStamp.untrusted`로 **무시**된다(오류가 아님). 우리 결과의 `timeStamp.untrusted`는 c2pa-rs 기본 설정에 DigiCert TSA 루트가 없기 때문[추정]. TSA 토큰은 TSA 인증서가 만료돼도 유효(§15.8). TSA 인증서 폐기 확인은 규격이 요구하지 않음(§15.8).
3. **체인**(§15.7): 서명 인증서 → 중간 → 신뢰 앵커. 못 닿으면 `signingCredential.untrusted`(우리 현재 상태). 앵커 자신의 notBefore/notAfter도 적용.
4. **폐기**(§15.9): 스테이플된 OCSP(`rVals`)가 "good"이고 응답 시각이 창 안이면 통과. 없으면 온라인 검증기는 조회해도 되지만(should) 어떤 파일을 검증하는지 노출되므로 선택 사항 → 건너뛰면 `ocsp.skipped`, 못 받으면 `ocsp.inaccessible`. **폐기 시각이 타임스탬프 시각보다 뒤면** 서명은 유효로 본다(removeFromCRL 제외). CA가 그 시각에 폐기돼 있었으면 `signingCredential.untrusted`. 오프라인 서명 후 나중에 넣을 수 있는 `c2pa.certificate-status`(OCSP 응답 묶음, §18.19)와 `c2pa.time-stamp`(§18.18) assertion도 있다.
5. 서명 자체(§15.7): COSE 서명 검증 실패는 `claimSignature.mismatch`.

### 4.3 C2PA 신뢰 목록 형식 [확인: 보고서 02 §3.3·출처 C4·C5 + 이번 재확인]
- 공식 목록은 `c2pa-org/conformance-public` 저장소 `trust-list/` 폴더의 **PEM 묶음**(인증서 33장, 2026-11-13 기준 02 보고서 집계) + 적합성 프로그램. 옛 임시 목록은 2026-01-01 동결. 검증기(c2pa-rs)는 `Settings`의 `trust.trust_anchor_certs`(앵커 PEM)·`trust.allowed_list`·`trust.trust_config`(허용 EKU)로 넣는다. 우리 `verify.js`는 c2pa-web `Context({trust:{trustAnchors: lab-root.pem}})`로 **연구실 루트를 앵커에 추가**하는 방식(verify.js 107~108행) — 규격이 말하는 "검증기가 어떤 앵커를 믿느냐"를 그대로 구현한 것.
- 목록 JSON 스키마가 따로 있는지(PEM 외)는 **확인 못 함**.

## 5. 멀티모달 지원 현황

### 5.1 설치된 SDK가 실제로 받는 형식 [확인: c2pa-python 0.38.0 / c2pa-rs 0.91.0, 이 세션에서 `get_supported_mime_types()` 호출]
| 종류 | 형식 | 읽기(Reader) | 쓰기(Builder) | 비고 |
|---|---|---|---|---|
| 이미지 | PNG, JPEG, GIF, WebP, TIFF, DNG, HEIC/HEIF, AVIF, JPEG XL, SVG | O | O | NEF·ARW(카메라 RAW)는 읽기만 |
| 영상 | MP4, MOV, M4V, AVI | O | O | **조각 MP4(DASH)는 Rust 라이브러리의 파일 API `Builder::sign_fragmented_files(signer, init_path, "video_*.m4s", out)`만** 지원, Python에 없음[확인: Python Builder 메서드 목록에 없음; c2pa-rs supported-formats.md]. 기존 매니페스트 있는 조각 파일은 미지원(docs.rs) |
| 음원 | WAV, MP3, FLAC, M4A(audio/mp4) | O | O | 쓰기 목록에 `audio/wav`, `audio/mpeg`, `audio/flac`, `audio/mp4` 모두 있음 |
| 문서 | **PDF** | **O** | **X**(쓰기 목록에 `application/pdf` 없음) | c2pa-rs 문서의 형식 표에는 pdf가 있으나 읽기 전용임을 명시하지 않음. 이 빌드에서 쓰기 불가는 호출로 확인 |
| 문서 | DOCX/PPTX/XLSX(+macro), ODT/ODS/ODP/ODG, EPUB, OXPS, ZIP | O | O | 규격 A.6 ZIP 계열(collection hash) |
| 텍스트 | txt, md, 코드 등 | X | X | c2pa-rs에 `unstable_plain_text`·`unstable_structured_text` 비공개 기능 플래그로만 존재(supported-formats.md). Python 빌드에는 없음 |
| 기타 | .c2pa(사이드카 매니페스트) | O | O | 모든 형식에 사이드카/원격 매니페스트 가능(`set_no_embed`, `set_remote_url`) |

### 5.2 규격 차원의 지원과 한계 [확인: 규격 2.4 부록 A, §19]
- **영상**: 통짜 MP4는 성숙(bmff.v3). 조각·라이브는 2.4에서 §19 "Live Video"로 정리됐고 두 방식(세그먼트별 매니페스트 상자 / `emsg` 세션 키 서명)이 있다. 한계: 트랜스코딩(해상도별 재인코딩)마다 **새 매니페스트가 필요**하고, 플레이어·CDN이 `uuid`·`emsg` 상자를 보존해야 한다. 브라우저 `<video>`는 검증기가 없다 → 우리 사이트에서 하려면 MP4를 통째로 내려받아 c2pa-web로 검증하는 방식만 가능[추정].
- **음원**: WAV(RIFF `C2PA` 청크)·MP3/FLAC(ID3 `GEOB`)·Ogg(별도 비트스트림) 모두 규격화. 한계: 스트리밍 플랫폼이 ID3를 다시 쓰는 일이 흔해 소실되기 쉽고, 등록된 음원 워터마크(WavMark·AudioSeal 계열·Digimarc 등)와 짝을 지어야 되찾기가 된다.
- **문서(PDF)**: 규격 A.4로 삽입 방법·증분 저장·전자서명 공존 규칙까지 정의돼 있지만 **공개 SDK 쓰기 구현이 없다**(위 표). Adobe Acrobat의 PDF Content Credentials 지원 여부는 이번에 **확인 못 함**(남은 질문).
- **텍스트**: 규격 A.8(변이 선택자)·A.9(BEGIN/END 블록)로 정의됐고, 알고리즘 목록에 텍스트 워터마크·핑거프린트가 7개 등록돼 있다(WritersLogic, Encypher, Cognitive-Proof). SDK는 비공개 기능. 복사·붙이기·포매터에 매우 약하다는 구조적 한계.

### 5.3 전 형식 공통 한계 [확인/추정 구분]
- 어떤 형식이든 엄격한 결속은 "바이트 그대로"만 보증하므로, **플랫폼 재인코딩 한 번에 증명서가 떨어진다**(개발일지 CBC 사례 보고 [확인]). 그래서 규격 자체가 느슨한 결속+저장소(§9.3, Soft Binding API)를 둔다.
- 매니페스트 용량: 영상·음원에는 썸네일이 상대적으로 작지만 TSA·인증서(약 12KB)는 그대로 붙는다[추정: 1.3절 분해에서].

## 6. 종합 — 우리 사이트를 영상·음원·문서까지 넓히는 3단계

전제: 서명은 노트북(개인키 보관처)에서, 검증은 브라우저(c2pa-web 0.17.0)에서, 원장은 정적 JSONL. 이 구조를 유지한다.

**1단계(다음 방문 전 가능, 코드 변경 최소) — 음원 WAV·영상 MP4를 지금 파이프라인으로 서명·검증**
- 무엇을: `tools/sign.py`는 MIME을 파일 확장자에서 추측해 `builder.sign(signer, mime, …)`에 넘기므로 WAV·MP4를 그대로 넣으면 c2pa-rs가 RIFF `C2PA` 청크 / BMFF `uuid` 상자로 삽입하고 WAV는 hash.data, MP4는 hash.bmff.v3를 자동 선택한다[확인: 5.1 쓰기 목록, 규격 A.5·A.3.7; 실제 서명 실행은 키가 없어 확인 못 함]. 샘플은 연구실 발표 녹음(WAV)·현장 영상(MP4) 각 1~2개.
- 왜: 추가 라이브러리 없이 "네 종류 중 셋"이 바로 된다. c2pa-web도 같은 c2pa-rs이므로 브라우저 검증이 그대로 된다[추정: c2pa-web 지원 형식 표는 확인 못 함].
- 함께 할 것: 서명 전후 용량, 어떤 편집(ffmpeg 재인코딩·메타데이터만 수정)에 깨지는지 2.3절 표를 **실험으로 확인**(이건 생각만으로 확정 못 하는 부분: c2pa-rs가 MP4 exclusions에 무엇을 넣는지).

**2단계 — 느슨한 결속을 규격 형식으로**
- 무엇을: (a) 매니페스트에 `c2pa.soft-binding`(alg `com.adobe.trustmark.Q`, value=워터마크 비트열) 추가. (b) 원장(ledger.jsonl)에 알고리즘 이름·값 열을 두고, `verify.js` 조회 결과에 `manifestId`·`similarityScore`(해밍 거리→0~100 변환) 필드를 붙여 Soft Binding API 응답 형태로 맞춤. (c) 음원·영상은 `scope.timespan`으로 구간별 값(예: 10초 단위 핑거프린트)을 넣는 실험.
- 왜: 지금 원장 조회는 우리만 읽는 형식이다. 규격 형식으로 두면 젠룩 포털의 저장소와 같은 API로 이어 붙일 수 있고, 발표에서 "규격의 어느 부분을 구현했는가"를 절 번호로 말할 수 있다(§18.10, Soft Binding API §1.4.1).
- 막힐 곳: 블록 DCT·lab-phash는 등록 이름이 없다. 자체 이름(예: 역도메인 표기)을 쓰되 "미등록"이라고 명시. 음원·영상 핑거프린트는 조사 06 주제.

**3단계 — 문서(PDF)와 텍스트**
- 무엇을: PDF는 공개 SDK 쓰기가 없으므로 ① **사이드카 매니페스트**(`set_no_embed` + `.c2pa` 파일 + hash.data로 PDF 전체 해시)로 먼저 해 보고, ② c2pa-rs 저장소의 PDF 쓰기 이슈/PR을 추적, ③ 상용(Adobe Acrobat 등) 지원 여부 확인. 텍스트(논문 초록 등)는 규격 A.8 변이 선택자 방식이 SDK 비공개 기능이라 **시연 범위에서 제외하고 조사만** 권고.
- 왜: 1·2단계가 되면 "네 종류 중 셋 + 문서는 사이드카"로 회사 목표의 모양이 갖춰지고, PDF 임베드는 SDK 지원을 기다리는 것이 자체 구현보다 안전하다(PDF 증분 저장·전자서명 공존 규칙 A.4를 직접 구현하면 오류 위험).
